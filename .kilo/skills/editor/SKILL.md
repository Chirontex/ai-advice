# Editor Skill: редакционная проверка документов

## Зачем этот скилл

Документы уходили пользователю с дефектами, которые автор в своей сессии не видит:
обрубки диалога («как я уже говорил выше»), отсылки к другой версии и к файлу,
которого читатель не получит, суммы, не сходящиеся с итогом таблицы, «1,500,000»
в русском тексте, аббревиатуры без расшифровки, ссылка на поиск маркетплейса
вместо карточки товара, мёртвый URL, канцелярит вдвое длиннее сути.

Модель не осматривает текст глазами, поэтому проверка строится на том, что
поддаётся механике: regex, разбор чисел и дат, HTTP-ответы серверов, пересчёт
в песочнице, словарная проверка. Всё, что механике не поддаётся (смысл,
понятность, самодостаточность), проверяется **читателем без контекста** —
отдельной сессии, которая видит только файл.

## Ключевой принцип

1. **Результат виден в документе, а не в рассказе о проверке.** Скилл не
   производит текста наружу: ни отчёта о прогонах, ни перечисления находок, ни
   файла вердикта. Чистый документ — и есть доказательство работы. Всё, что
   важно читателю (оговорка о свежести данных, граница применимости, риск),
   переезжает **в сам документ**; всё, что важно только проверке, не покидает
   её. Исключение одно: проверка не смогла состояться или упирается в факт,
   которого нет у тебя, — тогда это задаётся как вопрос по существу, а не как
   описание процесса.
2. **Проверка — исполнение, а не намерение.** Каждая находка скрипта либо
   исправлена, либо отброшена как ложная **осознанно, с понятной тебе причиной**.
   Молча пропущенная находка — то же самое, что непроверенный документ.
3. **Машина там, где можно; читатель там, где нужно.** Чеклист «на глаз»
   без скриптов не выполняется: он даёт иллюзию проверки.
4. **Документ живёт без сессии.** Всё, что понятно только тому, кто помнит
   разговор, — дефект документа, а не недостаток читателя.
5. **Редактор не автор.** Правки не меняют факты, выводы и голос автора.
   Не хватает факта — вопрос пользователю, а не домысел в тексте.
6. **Порог применения.** Ответ в три строки не требует редакторского прохода;
   документ, который пойдёт в ФНС, банку или арендодателю, требует полностью.

## Триггер использования

Применять, когда:

- составляется **документ, содержащий развёрнутый ответ** пользователю: файл в
  `develop/<тема>/` либо структурированный ответ в чате (заголовки, списки,
  таблицы, цифры, шаги);
- пользователь просит **вычитать, проверить, отредактировать, посмотреть на
  опечатки, сверить расчёты, убрать воду, добавить глоссарий или ссылки**,
  привести текст, чтобы был понятен сам по себе;
- текст **сторонний**: приложенный файл, вставленный фрагмент, договор, ТЗ,
  претензия, письмо, статья, служебка, резюме, описание товара;
- финализация документа перед сдачей или перед отправкой третьим лицам.

НЕ применять:

- короткий ответ без чисел, ссылок и терминов (тир Т0) — достаточно обычной
  самопроверки;
- вёрстку, слайды, постеры, инфографику — там навык `infographic` со своей
  геометрической верификацией;
- код — там навык `dev` со своим ревью-гейтом и чеклистом;
- распознавание сканов и рукописного текста — навык `ocr`;
- бинарные DOCX/PDF/XLSX: проверяется только извлечённый текст, сначала OCR
  или чтение содержимого.

## Тира применения

| Тир | Когда | Комплект |
|---|---|---|
| **Т0** | < ~10 строк, нет чисел, ссылок, терминов; не сохраняется файлом | не применять: самопроверка по инструкции агента |
| **Т1** | черновик в файле или ответ ~10–30 строк; расчётов ≤ 1, внешних ссылок нет, третьи лица не читают | чеклист руками + `doc_lint.py` + пересчёт чисел в Python |
| **Т2** | любой признак: ≥ 30 строк; есть деньги/сроки/дозы/ставки; есть внешние ссылки; термины, которыми неспециалист споткнётся; документ уйдёт третьим лицам или в госорган; содержание необратимо (договор, претензия, заявление, декларация); медицина или право; пользователь просил вычитать | все 4 скрипта + журнал расчётов + холодный читатель |

Тир выбирается в начале и **повышается, но не понижается** по мере работы:
если в «простом» ответе появились цифры и ссылки — он уже Т2. Спорные случаи
решаются в сторону более высокого тира: цена лишней проверки ниже цены
документа с неверной ставкой.

## Окружение и инструменты

- Python: `python` (в этом окружении 3.14; `python3` отсутствует). Перед первым
  запуском: `$env:PYTHONIOENCODING="utf-8"` — иначе кириллица в stdout ломается.
- Скрипты лежат в `.kilo/skills/editor/utils/`, запуск по абсолютному или
  относительному пути из корня проекта.
- **PowerShell: heredoc `<<` не работает.** Скрипты и JSON пишутся через `write`,
  затем выполняются отдельной командой. Цепочки — через `; if ($?) { ... }`.
- `requests` + `certifi` установлены и работают; стандартный `urllib` с
  системным хранилищем сертификатов в этом окружении падает на TLS — в
  скриптах это обработано.
- Код выхода всех скриптов: **0 — чисто, 1 — есть MAJOR, 2 — есть BLOCKER**
  (у `spell_ru.py` код 2 также означает отказ по приватности или недоступность
  сервиса). Не ограничивайся словом «проверил», пока не посмотрел коды выхода.
- Язык словарной проверки — русский (ru-RU); остальные проверки нейтральны к
  языку. Для английского текста профиль не настроен: опечатки ловятся только
  перечитыванием.

### Команды

```powershell
$env:PYTHONIOENCODING="utf-8"
$d = "develop\<slug>\<slug>.md"

# 1. локальные проверки: структура, остатки, глоссарий, числа, таблицы, вода
python .kilo\skills\editor\utils\doc_lint.py $d --asof 2026-11-10

# 2. ссылки: живость, назначение, форма, отсутствие ссылки там, где она нужна
python .kilo\skills\editor\utils\link_check.py $d --timeout 25

# 3. расчёты: пересчёт журнала и покрытие всех чисел документа
python .kilo\skills\editor\utils\calc_verify.py --doc $d --checks $env:TEMP\kilo\<slug>\calcs.json

# 4. орфография, пунктуация, грамматика (внешний сервис; см. «Приватность»)
python .kilo\skills\editor\utils\spell_ru.py $d --pii
```

Полезные флаги:

- `--internal` — служебные документы (конфигурация, инструкции, навыки,
  регламенты): отключает находку «утечка внутренней кухни» и понижает
  глоссарий до MINOR. Для читательских документов не используется.
- `--acronym-whitelist РФ,ООО,...` — снять ложные находки глоссария по
  общепонятным сокращениям; `--glossary-heading "глоссар|термины"` — если
  раздел назван иначе; `--max-sentence-words 28` — порог длины предложения.
- `--json` — машинный вывод, когда находок много и их нужно фильтровать.
- `doc_lint.py -` — чтение из stdin: `Get-Content $d | python ...doc_lint.py -`
  для черновика, который ещё не сохранён.
- `link_check.py --skip-network` — только форма ссылок и контекст, когда сети
  нет; граница фиксируется внутри проверки, а если она важна читателю —
  оговоркой в самом документе.

## Алгоритм работы

### Шаг 0. Тир и читатель

Определи тир (таблица выше) и **аудиторию документа**: сам пользователь,
клерк ФНС, арендодатель, работодатель, банк, врач. От аудитории зависят
глоссарий, допустимый жаргон и необходимость ссылок. Аудитория не названа —
используй контекст (user_context, тема запроса), не устраивай допрос.

Аудитория формулируется как **уровень погружённости, требуемый, чтобы задать
этот вопрос**, а не как «широта кругозора». Этот уровень — единственный
порог глоссария: всё, что читатель принёс с собой в формулировке вопроса,
объяснению не подлежит. Он же — уровень, который передаётся холодному
читателю в брифинге.

### Шаг 1. Черновик в файле (file-first)

Документ тира Т2 сначала пишется в `develop/<slug>/<slug>.md`, проверяется
там, потом пересказывается в чате. Причина: только файл поддаётся механической
проверке и повторным раундам; ответ «сразу в чате» проверяется по частям.
Для Т1 допустим черновик во временной директории или stdin.

Требования к самому файлу: имя = имя поддиректории, без `README`/`result`/
`output`. В `develop/<slug>/` лежит **только то, что читает пользователь**:
рабочие артефакты проверки (журнал расчётов, черновики прогонов, вывод скриптов)
в эту директорию не попадают — они живут во временной директории
`C:\Users\Dmitriy\AppData\Local\Temp\kilo\<slug>\`. Папка результата не должна
содержать следов твоей кухни.

### Шаг 2. Машина

Запусти комплект тира **в порядке: doc_lint → link_check → calc_verify →
spell_ru**. Порядок важен: doc_lint чистит структуру и числа, после правок
которые меняют текст, ссылки и расчёты перепроверяются заново (шаг 3–4),
а spell_ru — последний, потому что он самый дорогой и чувствительный к
переписанным фразам.

Собери находки в три кучи: **BLOCKER** (чинится обязательно), **MAJOR**
(чинится или отбрасывается осознанно), **MINOR** (чинится по стоимости:
если правка тривиальна — делай, если тянет за собой переписывание — отбрось).
Разбор находок — внутренняя работа: он не становится текстом для читателя,
кроме случаев, когда находка требует переезда в документ содержанием
(см. «Закрытие проверки»).

### Шаг 3. Журнал расчётов

Для Т2 с двумя и более расчётами заведи журнал **во временной директории**
(`%TEMP%\kilo\<slug>\calcs.json`) — он служит пересчёту, а не читателю:

```json
[
  {"label": "НДФЛ с продажи", "expr": "(8_000_000-5_000_000)*0.13",
   "expected": 390000, "note": "имущественный вычет 1 млн применён"},
  {"label": "Стаж владения", "expr": "years_between('2024-05-01','2026-11-10')",
   "expected": 2.53, "tol": 0.02}
]
```

Правила журнала:

- **каждое** число-результат в документе имеет запись в журнале: формула,
  ожидаемое значение, откуда взяты исходные данные;
- `expected` — то, что написано в документе, а не то, что получилось:
  расхождение и есть находка;
- цель прогона — `неверифицированных чисел=0`. Числа, которые не величины
  (номера статей, пунктов, частей статьи, индексы документов, годы, артикулы,
  номера домов), не подделываются под расчёт: они трассируются к источнику
  **в самом документе**, а в журнале просто отсутствуют;
- арифметика пересчитывается скриптом, а не в голове: модель ошибается в
  промежуточных шагах и округлении;
- формулы, нужные читателю, чтобы поверить числу, — **в тексте документа**
  (логика и промежуточные шаги), а не в служебном журнале: журнал у читателя
  не окажется.

### Шаг 4. Смысловой проход автора по чеклисту

Машина не видит смысл. Пройди по чеклисту вручную, по абзацам, а не по
впечатлению от целого текста. Особое внимание — пунктам, у которых механизм
«только человек»: противоречия утверждений, опоры на выводы, которых нет в
тексте, соответствие объёму запроса, риски.

### Шаг 5. Холодный читатель (Т2)

Запусти через `task` → `general` **новую сессию** (без `task_id`: свежий
контекст — суть проверки). Только чтение, без правок файлов. Шаблон брифинга —
раздел «Холодный читатель».

### Шаг 6. Правки по находкам читателя

Внеси правки, которые завёл читатель, и повтори машину для изменённых мест:
если текст переписан, находки `doc_lint` и `spell_ru` по нему снимаются
только повторным прогоном.

### Шаг 7. Сдача

Сдай документ: путь к файлу и суть ответа. О проверке не сообщай — она
видна в тексте (раздел «Закрытие проверки»). Наружу из проверки выходит
только то, что читатель обязан знать и чего в документ не поместилось, —
например, отсутствующий факт, который можешь дать только пользователь.

## Чеклист

Формат: **что проверяем → механизм → норма сдачи.**

1. **Опечатки и грамматика** → `spell_ru.py` (LanguageTool ru-RU: TYPOS,
   GRAMMAR, PUNCTUATION, CONFUSED_WORDS, LOGIC) + находки `doc_lint` MARKUP
   (удвоенные слова, омоглифы, парность) + перечитывание вслух.
   Норма: MAJOR закрыты все; известно, что LT не знает части имён собственных
   и брендов — их сверяет автор.
2. **Пунктуация и типографика** → `doc_lint` MARKUP: кавычки «» и скобки
   распарены, нет двойных пробелов, пробела перед `,` `.` `;` `:`, дефис
   вместо тире, тире без пробелов, прямые кавычки, апостроф в кириллице,
   разряды чисел по-русски, диапазоны через черту.
   Норма: нет BLOCKER/MAJOR; MINOR — по стоимости правки.
3. **Связность и согласованность терминов** → `doc_lint` GLOSSARY и NUMBERS +
   ручной проход: одна сущность называется одинаково во всём документе;
   нет разных названий для одной вещи («квартира»/«объект»/«жильё» вперемешку).
4. **Отсутствие противоречий** → только человек (шаг 4) и холодный читатель:
   утверждения в шапке, теле и выводе не расходятся; вывод следует из
   приведённых данных.
5. **Корректность расчётов** → `calc_verify.py` по журналу + покрытие чисел.
   Норма: расхождений 0, ошибок выражений 0, неверифицированных величин 0.
6. **Даты, сроки, дни недели** → `doc_lint` NUMBERS: несуществующие даты
   (31.02), год в будущем, день недели против даты, длительности.
   Норма: BLOCKER по датам устранён; сроки пересчитаны от реальной даты среза
   (`--asof`), а не от «сегодня» в голове.
7. **Таблицы** → `doc_lint` TABLES: итоги равны сумме строк, число колонок
   совпадает, пустые ячейки обозначены «—», заголовки колонок осмысленны.
8. **Самодостаточность** → `doc_lint` LEFTOVER (остатки диалога, отсылки к
   версиям, плейсхолдеры, внешние файлы, локальные пути, внутренняя кухня) +
   холодный читатель, который ловит то, что нельзя выразить regex: опору на
   незафиксированный вопрос, необъяснённый вывод, ответ «в никуда».
   Норма: BLOCKER по остаткам = 0; документ понятен человеку, который не
   знает, что его спрашивали.
9. **Понятность неспециалисту** → холодный читатель отвечает на контрольные
   вопросы по одному только тексту + `doc_lint` WATER (средняя и максимальная
   длина предложения, канцелярит).
   Норма: читатель отвечает на все вопросы без догадок; предложения длиннее
   порога разбиты там, где это меняет восприятие.
10. **Гиперссылки на контекст** → `link_check.py`: каждая ссылка открывается
    (или честно помечена как требующая входа), ведёт на конкретную страницу,
    а не на главную и не на поиск, текст ссылки сообщает назначение,
    маркетплейс-ссылка содержит артикул, абзацы про цену/модель/артикул/ставку
    имеют источник.
    Запрет: **URL не выдумываются.** Источник каждой ссылки — ввод пользователя,
    результат поиска этого же прогона или проверенный live. Не проверяется —
    убирается или заменяется ссылкой на главную страницу источника с пометкой.
11. **Глоссарий** → порог включения один: **термин лежит за пределами
    компетенции, необходимой читателю, чтобы задать этот вопрос.** Своё поле
    читатель знает — разъяснять его шумно и оскорбительно; объясняется только
    чужое поле, в которое документ его ведёт (нормативка, смежные профессии,
    их жаргон, аббревиатуры регуляторов). Дополнительно: статья ставится,
    только если термин повторяется или влияет на решение; единичное
    упоминание раскрывается скобками при первом употреблении и в глоссарий
    не переезжает. Механизм: `doc_lint` GLOSSARY собирает кандидатов и
    молча не решает за тебя — расширение списка «известно аудитории»
    (`--audience-known`) снимает находки по своему полю читателя.
    Признаки перебора: статья объясняет то, что было в формулировке запроса
    пользователя; объясняет общешкольные аббревиатуры (ИИ, ПО, ML, ДД/ММ);
    в статье больше слов, чем в абзаце, где термин употреблён.
12. **Вода** → `doc_lint` WATER: канцелярит, номинализации, усилители без
    содержания, служебные переходы, чат-остатки («надеемся, поможет!»),
    мета-комментарии о самом документе, дословные самовторы, дублирование
    абзацев, повтор вывода в шапке и в конце.
    Норма: предложение удаляется без потери информации → оно удалено.
13. **Факты и свежесть** → отметка «актуально на ДД.ММ.ГГГГ» при нормах,
    ставках, ценах, версиях; у каждой цифры-нормы указан источник; данные,
    которые меняются, помечены «проверь перед подачей».
    Механизм: `doc_lint` STRUCTURE + совпадение с источниками поиска.
14. **Соответствие объёму запроса** → матрица «подвопрос пользователя →
    раздел документа»; ничего не пропущено, ничего не добавлено «заодно».
    Механизм: контрольные вопросы холодного читателя = подвопросы запроса.
15. **Практическая применимость** → шаги в императиве с конкретикой (куда
    идти, что взять, какой срок, что делать при отказе), а не «рекомендуется
    рассмотреть возможность». Механизм: человек + холодный читатель
    («сможешь повторить шаги по тексту?»).
16. **Риски и границы в самом документе** → блок о том, что может пойти не
    так, и когда нужен живой специалист; для медицины/права/денег обязателен,
    без паники и без замены содержания.
17. **Приватность и секретность** → нет персональных данных третьих лиц шире
    необходимого, нет токенов, ключей, внутренних адресов, логинов; наружу
    текст уходит только по правилам раздела «Приватность».
18. **Форматы и единицы** → валюты и единицы измерены единообразно (₽ или
    «руб.», но не оба), даты в одном формате, время в 24-часовом, проценты и
    доли не путаются, регистр и написание юрлиц, ФИО, топонимов, продуктов
    сверены с источником.

## Холодный читатель

Смысл: сессия автора знает то, чего не знает документ. Читатель без контекста
проверяет пункты 4, 8, 9, 11, 14, 15 за один проход.

Брифинг (подставь путь и 3–6 контрольных вопросов — подвопросов запроса):

```
РОЛЬ: ты впервые читаешь документ, контекста сессии у тебя нет. Тема и цель
не сообщаются намеренно.
УРОВЕНЬ ЧИТАТЕЛЯ: <компетенция, необходимая, чтобы задать этот вопрос> —
например, «senior backend-разработчик 7 лет, тимлид, интересуется ИИ».
Ты владеешь этим уровнем полностью: термины своего поля (названия ролей,
технологий, аббревиатуры вроде ИИ/ПО/ML/API) тебя не спотыкают, и требовать
их расшифровки НЕЛЬЗЯ — это шум. Спотыкает тебя только то, что лежит за
пределами этого уровня: нормативка, чужие профессии, их жаргон, аббревиатуры
органов, узкие обозначения.
ФАЙЛ: прочитай целиком <path> через read. Больше ничего не читай, не ищи
в сети, не опирайся на догадки о том, что «имелось в виду».
ПРАВА: только чтение. Не редактируй файлы, не запускай изменяющие команды.

КОНТРОЛЬНЫЕ ВОПРОСЫ (ответь ТОЛЬКО по тексту документа, цитируя строки):
1. <подвопрос 1>
2. <подвопрос 2>
...
N. Сможешь ли ты, владея указанным уровнем, выполнить действия из документа
   самостоятельно? Перечисли, где застрянешь и почему.

ВЕРНИ В ФОРМАТЕ:
1) ОТВЕТЫ на контрольные вопросы: вопрос → ответ из текста → цитата/строка.
   Если ответа в документе нет — так и напиши: «в документе ответа нет».
2) САМОДОСТАТОЧНОСТЬ: места, где нужны внешние знания, память о разговоре,
   другой документ или другая версия текста (номер строки + что не хватает).
 3) НЕПОНЯТНОЕ: термины, аббревиатуры, формулировки, которые спотыкают
    при указанном уровне; предложения, которые пришлось перечитывать.
    Термины своего поля не перечисляй — они по условию понятны.

4) ПРОТИВОРЕЧИЯ: пары утверждений, которые не сходятся (строки + почему).
5) ЧИСЛА: какие величины ты не смог воспроизвести или понять, откуда они.
6) ВОДА: абзацы и фразы, которые можно удалить без потери информации.
7) ЛИШНЕЕ/НЕДОСТАТКОЕ: что в документе не по теме и чего не хватает.
8) ВЕРДИКТ: PASS | REQUEST_CHANGES + три главных замечания по влиянию на
   читателя.

Если нужно разрешить противоречие между утверждениями документа — веди
разбор через sequential-thinking: гипотеза → проверка шагом цепочки →
верификация вывода последним шагом. Чистое чтение цепочки не требует.
```

Правила:

- контрольные вопросы формулируются **из запроса пользователя**, а не из того,
  что документ случайно содержит;
- уровень читателя в брифинге — тот же, что определён в шаге 0: компетенция,
  требуемая, чтобы задать вопрос. Занижать его нельзя: читатель «с улицы»
  потребует объяснить половину документа, и эти правки будут вредны;
- читателю не сообщаются ответы, выводы и объяснения автора — иначе проверка
  становится пересказом;
- находка читателя «не понял» исправляется в документе, а не объясняется
  пользователю в чате: документ должен стоять сам;
- повторная проверка — резюме той же сессии читателя (контекст сохранён), но
  вывод он строит по обновлённому файлу, а не по утверждениям о правках.

## Дисциплина правок

1. **Факты не правятся на глаз.** Ставка, норма, доза, цена, дата, имя,
   артикул меняются только с подтверждённым источником; нет источника —
   вопрос пользователю, а не «близкое значение».
2. **Голос автора сохраняется.** В стороннем тексте редактируются форма и
   ясность, а не интонация: авторские обороты, терминология и структура
   остаются, если не мешают пониманию. Переписывание под свой стиль — дефект
   редактора.
3. **Содержательные правки отличимы от косметики.** Косметика (опечатки,
   пунктуация, форматы) видна читателю как чистый текст. Содержание (цифры,
   формулировки выводов, удалённые или добавленные абзацы) меняется только
   там, где есть основание; если правка меняет вывод или факт и это
   сомнительно — вопрос автору, а не тихая подмена.
4. **Никакого «заодно».** Не добавляй разделы «для полноты», не расширяй тему,
   не включай в документ то, о чём не спрашивали. Попутный риск, влияющий на
   применение документа, — строка в блоке рисков документа; не влияющий —
   не попадает никуда.
5. **Удаление — тоже правка.** Вырезая воду и повторы, не теряй факт: если
   фраза несла информацию, она осталась в сжатом виде.
6. **Правки не ломают проверенное.** После переписывания абзаца его находки
   `doc_lint`/`spell_ru` считаются недействительными до повторного прогона.

## Приватность

`spell_ru.py` — единственная проверка, уходящая во внешний сервис.

- Скрипт сам ищет признаки персональных данных (ФИО, паспорт, СНИЛС, ИНН,
  адрес с номером дома/квартиры) и **отказывается отправлять** текст, пока не
  выбран режим: `--pii` (замаскировать ПИИ и отправить остальное) или
  `--allow-send` (сознательное согласие).
- Всегда маскируются: URL, email, пути, код, телефоны, длинные номера,
  латинские токены. Маскирование схлопывает пробоины и подавляет находки
  впритык к замаскированному участку — это осознанный обмен: меньше шума,
  но опечатка вплотную к URL может остаться непойманной (её ловит шаг 4).
- Документы, содержащие персональные данные третьих лиц, врачебную или
  коммерческую тайну, секретные ключи, наружу не отправляются: орфография
  закрывается перечитыванием и локальными паттернами `doc_lint`.
- Ссылки: `link_check.py` ходит по адресам из документа, но не отправляет
  содержимое документа.
- Нужна постоянная проверка орфографии без внешних сервисов — подними локальный
  сервер LanguageTool (проверенные образы: `erikvl87/languagetool`, порт 8010;
  `meyayl/docker-languagetool`, порт 8081) и передай
  `--endpoint http://localhost:8010/v2/check`.

## Закрытие проверки

Проверка закрывается **документом**, а не отчётом. Внутренний контроль
завершённости (держится в голове или во временной директории, наружу не
выводится и в файл в `develop/` не ложится):

```
тир: Т1|Т2   раунд: N/2   аудитория: <кто читает>
машина: все прогоны комплекта тира выполнены, коды выхода посмотрены
находки: BLOCKER закрыты; MAJOR закрыты или отброшены осознанно; MINOR разобраны
числа: расхождений 0; не-величины трассированы к источнику в тексте
читатель (Т2): контрольные вопросы закрыты текстом или эскалированы
остаток: что важно читателю → переехало в документ; что не важно → молча закрыто
```

Каждая находка получает один из трёх исходов:

1. **Исправлена** — в документе.
2. **Отброшена как ложная** — причина понятна тебе, в документ не попадает.
3. **Переехала в документ содержанием** — если находка означает что-то, что
   читатель должен знать (данные свежие только на дату среза, источник
   косвенный, граница применимости, риск), она формулируется **в тексте**
   — оговоркой, аннотацией источника, блоком рисков. Не как признание в том,
   что ты это проверял.

Наружу из проверки выходит ровно две вещи: сам документ и — исключительно
когда без этого нельзя — вопрос пользователю о факте или решении, которого у
тебя нет. Всё остальное молчание: «проверил, нашёл 55 ложных срабатываний,
вот что исправил» — это отчёт о процессе, он не увеличивает ценность
документа и отнимает у читателя время.

**Молчание честно только когда проверка состоялась.** Если контроль прошёл
неполно — сеть недоступна, сервис отклонён, интерпретатор не найден, — это
сообщается одной строкой как граница результата: иначе непроверенное выдаётся
за проверенное. Это оговорка о качестве ответа, а не пересказ прогонов.

**Лимит раундов: два.** После второго раунда с незакрытым BLOCKER — остановка
и вопрос пользователю по существу (какого факта, доступа или решения не
хватает). Третья передка без человека бессмысленна.

## Анти-паттерны (проверено на практике)

| Плохо | Хорошо | Почему |
|---|---|---|
| «Как я уже говорил выше, ставка 13%» | «Ставка НДФЛ — 13% (п. 1 ст. 224 НК РФ, редакция на 10.11.2026)» | читатель не знает, кто «я» и о чём договаривались |
| «В нашем разговоре мы обсуждали…» | убрать или вписать вывод в текст | обрубок диалога = потерянный контекст |
| «Детали — в файле otchet-2026.pdf» | вставить нужную выжимку сюда | документ, которого читатель не получит, не существует |
| «См. предыдущую версию, там было иначе» | актуальное утверждение без сравнения | версия — не контекст читателя |
| «Продано за 8 150000 рублей» | «за 8 150 000 ₽» | сломанная группировка разбирается двояко |
| «База 1,500,000 минус 1 000 000 = 137 500. Итог: 137 000 ₽» | одно значение, пересчитанное скриптом | две близкие суммы = опечатка или потерянный член |
| Итог таблицы 2 500 000 при сумме строк 13 000 000 | пересчитать и сверить | таблица читается как факт |
| «подача декларации — в среду 10 ноября 2026» | «во вторник 10 ноября 2026» | день недели проверяется по календарю |
| «Дата сделки 31.02.2026» | существующая дата | такой даты нет, документ теряет доверие |
| «Ставка выросла на 150%» | «выросла в 2,5 раза» или корректный процент | процент > 100 почти всегда путаница % и доли |
| «НДФЛ, УСН, ИИС, ОФЗ, ROI» без расшифровки | глоссарий + расшифровка при первом употреблении | неспециалист спотыкается и бросает читать |
| Глоссарий к вопросу senior-разработчика: «ИИ — искусственный интеллект», «ПО — программное обеспечение», «ML — машинное обучение» | убрать статьи | читатель пришёл с этим словарём: объяснять его поле — шум и снисходительность |
| Единичный термин получил и скобки, и статью глоссария | оставить скобки при первом употреблении | раздутый глоссарий размывает статьи, которые реально нужны |
| «Полная таблица — [сюда](https://…)» | «[раздел ФНС «Декларация 3-НДФЛ»](https://…)» | текст ссылки должен сообщать назначение |
| Ссылка `ozon.ru/search/?text=гитара` | ссылка на карточку с артикулом | читатель попадает в каталог, а не в товар |
| «Осуществляется расчёт налога по двум сценариям» | «Считаем налог в двух сценариях» | номинализация = вода |
| «Следует отметить, что в настоящее время данный вопрос требует отдельного рассмотрения» | удалить или заменить фактом | ноль информации, три строки объёма |
| «Надеемся, это поможет! Таким образом, мы с вами разобрали расчёт» | убрать | чат-остаток, не документ |
| «Проверено через sequential-thinking и скилл editor» | убрать | внутренняя кухня читателю не нужна |
| «Это это важный момент» | «Важный момент» | удвоенное слово — типовая опечатка сборки |
| Раздел «Сценарий 2» без текста | заполнить или удалить | пустой раздел = обещание без поставки |
| «Прогнал doc_lint: BLOCKER=0, MAJOR=1, вот что исправлено…» | отдать чистый документ | отчёт о процессе — шум: проверка видна в тексте |
| Файл `-review.md` рядом с документом | удалить: следов проверки в папке результата нет | папка читает пользователь, а не ты |

## Definition of Done

- [ ] Тир определён и не понижен по ходу работы; комплект проверок запущен,
      коды выхода просмотрены
- [ ] BLOCKER = 0 во всех четырёх прогонах
- [ ] Каждая MAJOR-находка разобрана: исправлена или отброшена как ложная
      с понятной причиной
- [ ] MINOR разобраны по стоимости: тривиальные исправлены, затратные отброшены
- [ ] Журнал расчётов (во временной директории) заведён, расхождений 0,
      неверифицированных величин 0; номера, индексы и годы, которые не являются
      величинами, трассированы к источнику в тексте
- [ ] Все ссылки открываются или помечены как непроверяемые; ни одна не
      выдумана; текст ссылки сообщает назначение; товарные ссылки — карточки
- [ ] Глоссарий содержит только термины за пределами уровня аудитории,
      нужного задать вопрос; единичные термины раскрыты скобками, а не статьёй;
      своих полей читателя (его профессиональный словарь) глоссарий не касается
- [ ] Нет остатков диалога, отсылок к версиям, внешних файлов, плейсхолдеров,
      внутренней кухни
- [ ] Таблицы сходятся, форматы чисел/дат/валют единообразны, даты существуют,
      дни недели верны
- [ ] Воды нет: каждый абзац несёт информацию, самовторов и дублей нет
- [ ] Отметка актуальности стоит, нормы и цены имеют источники
- [ ] Объём соответствует запросу: все подвопросы закрыты, лишнего нет
- [ ] Шаги применимы: императив, конкретика, сроки, план при отказе
- [ ] Риски и «когда нужен специалист» — в самом документе
- [ ] Холодный читатель (Т2) ответил на контрольные вопросы по тексту;
      его замечания закрыты или эскалированы
- [ ] Приватность соблюдена: ПИИ наружу не уходили без согласия
- [ ] Раундов ≤ 2; остаточные блокеры эскалированы пользователю

## Сторонний текст (вычитка чужого)

Когда текст не мой (приложенный файл, вставленный фрагмент, договор, ТЗ,
письмо):

1. Уточни цель, если не ясна: «исправить только ошибки» или «и переписать
   ради ясности»? Без ответа — режим минимального вмешательства: опечатки,
   пунктуация, форматы, внутренняя согласованность, расчёты; стиль не трогаю.
2. Проверка та же: скрипты + смысловой проход. Холодный читатель обязателен,
   если текст адресован третьим лицам или имеет правовые последствия.
3. Возвращай **исправленной копией** (`<slug>-edited.md`, оригинал не
   перезаписывай): косметика видна в тексте и не пересказывается. Отдельно —
   только то, что требует решения автора (п. 4) или сверки с источником (п. 5).
4. Спорные места, где правка меняет смысл (формулировка обязательства, срок,
   штраф, сумма, условие отказа), не решай сам: выноси в блок «вопросы автору»
   с вариантом формулировки.
5. Факты, которые не подтверждаются (ставка, норма, имя, дата), помечай
   «требуется сверка с источником», а не исправляй догадкой.
6. Если текст юридически или медицински значим — скажи прямо, что редакторская
   проверка не даёт правовой и диагностической валидности: нужен профильный
   специалист (и призови его отдельной задачей, если пользователь просил
   разобраться по существу).

## Troubleshooting

- **LanguageTool недоступен, 403/429, таймаут.** Скрипт отмечает чанк как
  UNVERIFIED и выходит с кодом 2. Не выдавай отсутствие проверки за чистоту:
  орфографию добирают перечитывание + `doc_lint` MARKUP, а неполнота контроля
  сообщается пользователю (см. «Закрытие проверки»: молчание честно только
  когда проверка состоялась). Для регулярного использования подними локальный
  сервер (`erikvl87/languagetool` или `meyayl/docker-languagetool`) и передай
  `--endpoint`.
- **Сеть недоступна вовсе.** `link_check.py --skip-network` проверяет форму
  ссылок и контекст; живость остаётся неподтверждённой — это сообщается как
  граница результата, а не как отчёт о прогоне.
- **Маркетплейсы и госсайты отвечают 403.** Это антибот, а не мёртвая ссылка:
  не помечай как DEAD. Варианты: открыть вручную и подтвердить, заменить
  источник на проверяемый (официальная страница, агрегатор без защиты),
  оставить ссылку с пометкой «страница требует открытия в браузере».
- **Ложные срабатывания глоссария или воды.** Настраивай аргументами
  (`--acronym-whitelist`, `--glossary-heading`, `--max-sentence-words`), а не
  отключением проверки: отключённый чеклист молча теряет покрытие.
- **`python` не найден.** Скрипты неработоспособны: проверь
  `python --version`/`py --version`, иначе переходи на ручной смысловой проход
  и предупреди пользователя, что контроль снижен до перечитывания.
- **Примеры дефектов в кавычках.** Цитаты-образцы («как я уже говорил выше»,
  «Это это важный момент») ловятся `spell_ru` как настоящие ошибки — это
  ожидаемый шум: `doc_lint` и `link_check` такие места сознательно пропускают
  (текст в «» — пример чужой речи, а не речь документа), а орфографическая
  проверка кавычки не скрывает, потому что опечатка в процитированном договоре
   остаётся опечаткой. Разбирай находки внутри кавычек вручную и держи их как
   намеренный пример, а не как дефект документа.
- **Огромный документ.** Не гоняй всё вручную: дели по разделам, проверяй
  каждый файл целиком, а перекрёстные согласованность и повторы — отдельным
  прогоном по собранному документу.
- **Документ не Markdown, а текст в чате.** Сохрани черновик во временной
  директории и проверь файл: проверка «на глаз» ответа в чате не засчитывается.
  Режим `doc_lint.py -` (stdin) существует и даёт те же находки, что и файл,
  но полагаться на него нельзя: непроверенный черновик в чате не имеет точки
  повторного прогона.

## Границы

- Не заменяет фактчекинг: содержание и источники проверяются SOP Советника
  (поиск, субагенты), скилл проверяет оформление, связность и арифметику.
- Не даёт правовой, медицинской и финансовой валидности выводов.
- Не трогает вёрстку, графику, слайды и геометрию текста — это `infographic`.
- Не проверяет код в блоках: fenced-блоки исключены из разборов; код — `dev`.
- Не работает с бинарными DOCX/PDF/XLSX напрямую: сначала извлечение текста.
- Орфография — ru-RU профиль; для других языков словарная проверка не настроена.
- Не гарантирует ноль опечаток: словарь не знает части имён собственных,
  брендов и неочевидных омофонов; остаточный риск закрывается перечитыванием
  и холодным читателем.
- Не редактирует документационные артефакты других навыков (манифесты
  оркестрации, диффы ревью) — они служебные, их тир — Т1 с `--internal`.

## Файлы и артефакты

```
develop/<slug>/<slug>.md            документ — единственный файл результата
develop/<slug>/<slug>-edited.md     исправленная копия стороннего текста
                                    (только когда текст сторонний)
%TEMP%\kilo\<slug>\calcs.json       журнал расчётов (Т2) — вне develop/
```

В `develop/<slug>/` не появляется ничего, что служит проверке, а не читателю:
ни вердиктов, ни журналов, ни списков находок, ни логов прогонов. Именование —
по правилам Working Directory: имя файла = имя поддиректории, говорящий суффикс
для версий и ролей, безликие `README`/`result`/`output` запрещены. Временные
фикстуры и прогоны — во временной директории.
